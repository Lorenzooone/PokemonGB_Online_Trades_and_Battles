Korean to English:
0x21 (0x20) bytes + 0x8 (7) bytes for the name (0x20 bytes missing from message and 3 name bytes missing).
Mark as "K" to save it's from Korean mail.
Each Korean character (2 bytes, or 16 bits) can be packed in 12.5 bits (8 for the byte to be displayed, 1 bit for a "bad English byte", 3.75 bits for the corresponding 0-B table). Technically there are 320 (realistically 312, probably less due to the newline, which is not fixed in KOR) bits available, accounting for 24 characters (23 with the newline issue, which does become the 24th character technically). Removing the 5 of the trainer, this means 19 characters could be fit in theory (instead of the base 16 while cutting the trainer to just 2, for a net gain of 6 bytes without displaying bad stuff).
There would be 3 bytes for "bad Englsh byte" and 12 bytes for the table. The 3 "bad English bytes" can be hidden after the end of the trainer name, with four bytes of the trainer name going to the message part (avoid abusing the extra "language byte" to keep compatibility with Japanese, since we only need one, not two, hence the 312). For the 12 bytes, they can be in the message, but if the resulting value is a "bad English byte" (a control code), they can be converted to values that would normally be impossible with just 4 bit table (0-B) selection. Due to Japanese compatibility, bytes 0 of the message data and [5, 6] of the author data can get reset, so the last bytes must go there to keep the rest of the message coherent.
Technically it is 12.5 bits per Korean character by abusing the fact that there are 11 possible tables, meaning two chars have "just" 121 possible table values.

But would the increase in complexity be worth it...? It would make "Korean to Japanese" and viceversa harder too on the Japanese side of things.
